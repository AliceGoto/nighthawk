> 本文覆盖整体架构、Agent 循环、安全引擎与工程体系的常见追问。

## 项目 30 秒介绍（开场白模板）

"我做了一个安全为先的终端 AI Agent，叫 NightHawk。它的核心命题是：进攻性安全和严肃工程应该在同一个 agent 里——一个 Turn/Step 循环的编程 agent 内核，加上原生的安全引擎（116 条映射 CWE/OWASP 的规则、熵值密钥检测、污点分析、依赖审计），安全工具和读写文件、跑 shell 一样是一等工具。TypeScript monorepo，多 provider 抽象，TUI 终端原生。"

## 一、整体架构

**Q: 为什么拆成 agent-core / kosong / kaos 这样的分层？**
A: 关注点分离到可独立测试的边界——`kosong` 管"模型后端是可互换协议"（provider 抽象），`kaos` 管执行环境（文件/进程抽象，本地或远程），`agent-core` 管编排（循环、工具、会话、权限）。换模型不动引擎，换执行环境不动循环。CLI 应用只通过 SDK 消费内核，不直接依赖实现。

**Q: NightHawk 的 Agent 循环和普通的 ReAct 有什么区别？**
A: NightHawk 并不是按 Plan/Act/Observe/Reflect 四个显式阶段开发的。实际实现是一个 Turn/Step 循环：用户输入进入 Turn，每个 Step 由“LLM 请求 → 工具执行 → 结果写回上下文”组成，循环直到模型不再请求工具或达到步数上限。Plan 模式是可选用户模式，不是循环阶段；观察和反思主要通过上下文管理、子 Agent 隔离、提示词注入和事件机制实现，而不是独立的 Observe/Reflect 状态。

**Q: 子 agent 的价值是什么？**
A: 三个词：隔离、并行、聚焦。子任务（如"扫完这 40 个文件"）在子 agent 的独立上下文里跑完，只把结论带回主循环——主上下文的 token 花在决策上，不花在过程上。

## 二、安全引擎（差异化核心）

**Q: 规则扫描（SecurityScan）不就是一堆正则吗，价值在哪？**
A: 正则是执行机制，价值在工程化：每条规则带 CWE/OWASP 编号、严重度、中英双语修复建议；规则按语言过滤（`rulesForLanguage`）；和 agent 循环组合成工作流——规则命中作为污点分析的种子，污点流确认可利用性，这是"扫描器报告"到"可行动判断"的差别。单看一条正则当然简单，116 条规则的分类体系和它们与 agent 的组合方式才是工作量。

**Q: 污点分析（TaintTrace）怎么做的？为什么是文件级而不是全程序？**
A: 变量级污点追踪：识别用户可控源（HTTP 参数、env、stdin），沿赋值链（最多 3 轮）追踪到危险汇点（exec、eval、innerHTML、SQL）。不做跨文件全程序分析是精度/成本权衡——变量级在毫秒内出结果、零误报放大，agent 可以在一个回合里对可疑文件反复跑；全程序分析留给专业 SAST 工具，通过 MCP 接入即可。

**Q: SecretScan 为什么用 Shannon 熵？**
A: 已知前缀模式（AKIA... 等）抓得住已知格式的密钥，但抓不住自签 token 和私有格式。随机生成的秘密在字符分布上呈现高熵——熵评分是不依赖格式先验的兜底信号。

**Q: 和直接跑 Semgrep / CodeQL 比，你这个 agent 化安全有什么优势？**
A: 传统 SAST 的输出是报告，消费报告的是人。agent 化之后消费发现的是同一个 agent：它可以立刻用 TaintTrace 验证可利用性、读相关代码确认上下文、直接给出修复 diff。工具产出→验证→修复闭环在一个会话里完成。同时专业引擎仍可通过 MCP 接入——我提供的不是替代而是编排层。

## 三、工程体系

**Q: 这个项目怎么保证质量？**
A: 四层：
1. **契约钉死**——客户端 SDK 每个方法都有 zod schema，和引擎类型做编译期一致性断言，类型漂移在构建期爆
2. **传输一致性**——同一套测试跑在 memory 和 IPC 两种传输上，要求字节级一致
3. **安全引擎冒烟**——已知漏洞样本驱动四个安全工具
4. **仓库守卫**——lint 期强制导入边界、workspace 同步、打包完整性

**Q: 多 provider 支持具体怎么抽象的？**
A: provider 层把"模型后端"抽象成协议——OpenAI 兼容、Anthropic 原生、各家特有能力（思考模式、工具选择协议）作为 capability 声明。上层只声明需求，kosong 解析到具体后端。任何一个 OpenAI/Anthropic 兼容端点（含 DeepSeek、本地推理服务）接上即用。

**Q: 为什么 TUI 而不是 Web IDE 形态？**
A: 目标用户（安全工程师）的工作环境经常是 SSH 到跳板机/靶机——浏览器到不了那里,终端永远到得了。TUI 毫秒级启动、单二进制分发。TUI 层基于 pi 风格的组件化框架，有主题/i18n/Markdown 渲染,体验对标 GUI。

## 四、开放性问题（考察深度）

**Q: 这个项目最技术含量的一点？**
A: 建议答 compaction 的可重放设计（见 memory.md）或 MCP 工具转译层（见 mcp.md）——两者都有"为什么这样设计"的清晰权衡链。

**Q: 如果重新做一遍会改什么？**
A: 可答：一开始就把安全发现建模成结构化数据（而非文本报告），让 agent 的后续推理能直接消费 severity/CWE 字段做排序和去重；检索式记忆更早介入,减少重复说明上下文。

**Q: 下一步路线？**
A: 渗透测试方向的主动验证（agent 生成 PoC 验证发现）、MCP 接入专业 SAST/DAST 工具生态、检索式长期记忆、以及 benchmark 化的编码能力对比（SWE-bench 类基准）。
